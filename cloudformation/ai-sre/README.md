# Better Stack AI SRE

`better-stack-ai-sre.yaml` creates one read-only IAM role that Better Stack AI SRE assumes to investigate incidents in your AWS account, and two IAM policies that hold the role's denies. The stack has no other resources: no Lambda functions, no buckets, nothing that runs or stores data.

See the [main README](../../README.md) for the rest of this repository.

## Quick Start

Better Stack gives you a link that opens the AWS console's quick-create page with this template and your parameters filled in. Review the stack there, acknowledge that it creates a named IAM role, and create it. Better Stack finds the role by itself; there is nothing to paste back.

The latest release is published at `https://better-stack-cloudformation.s3.amazonaws.com/better-stack-ai-sre.yaml`, and every release at `https://better-stack-cloudformation.s3.amazonaws.com/<version>/better-stack-ai-sre.yaml`, which is never overwritten. You can download either one and deploy it yourself:

```bash
curl -fsSLO https://better-stack-cloudformation.s3.amazonaws.com/better-stack-ai-sre.yaml

aws cloudformation deploy \
  --template-file better-stack-ai-sre.yaml \
  --stack-name betterstack-ai-sre-XXXXXXXX \
  --parameter-overrides ExternalId=bs-ai-sre-XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX \
  --capabilities CAPABILITY_NAMED_IAM
```

The stack can be deployed in any region; IAM roles are global.

## What it creates

One IAM role, `better-stack-ai-sre-role-<8 hex>`, where `<8 hex>` is the first eight hex digits after `bs-ai-sre-` in the external ID. It's tagged `Solution: BetterStack` and `BetterStackAiSreTemplateVersion: <release>`, the release of this template that made it.

Only Better Stack's AI SRE callers for the chosen environment can assume the role, and only with the external ID Better Stack generated for your integration. A second trust statement lets the same callers set a source identity that starts with `bs-`, so that your CloudTrail can attribute AI SRE's calls; it grants no access by itself.

The stack also creates two customer managed policies, `better-stack-ai-sre-deny-data-<8 hex>` and `better-stack-ai-sre-deny-stored-data-<8 hex>`, attached to the role in both settings. They hold the denies listed in [What the role can't read](#what-the-role-cant-read), which don't fit in the role's own inline policies. With `AllowConfigurationValues=true`, the default, the role also has AWS's managed [`ReadOnlyAccess`](https://docs.aws.amazon.com/aws-managed-policy/latest/reference/ReadOnlyAccess.html) policy attached. The stack creates nothing else.

| Output | Description |

## Parameters

| Parameter | Default | Description |
|-----------|---------|-------------|
| `ExternalId` | (required) | Generated by Better Stack for your integration. Don't change it. |
| `BetterStackTeam` | `''` | The Better Stack team and organization that get access, shown in the role's description. Check it is yours. |
| `BetterStackEnvironment` | `production` | Which Better Stack environment may assume the role: `production`, `staging` or `development`. |
| `AllowConfigurationValues` | `true` | When `true`, the role gets AWS's `ReadOnlyAccess` policy, with secrets, credentials and stored data denied. When `false`, it gets a fixed, shorter list of reads and denies every read Better Stack knows returns environment variables, user data or parameter values (see below). |
| `PermissionsBoundaryArn` | `''` | A permissions boundary your organization requires on new roles. Optional. |

## What the role can read

With `AllowConfigurationValues=true`, the default, the role has AWS's [`ReadOnlyAccess`](https://docs.aws.amazon.com/aws-managed-policy/latest/reference/ReadOnlyAccess.html), which AWS extends as it adds services, plus the reads in the inline policy `BetterStackAiSreBroadAccess` that `ReadOnlyAccess` lacks: CloudTrail Lake queries, Performance Insights analysis reports, and the read-only tools of AWS's hosted EKS, ECS and Application Signals MCP servers. The reads in [What the role can't read](#what-the-role-cant-read) are denied on top. Configuration values such as environment variables are readable (see [Configuration values](#configuration-values)).

Outside the denied list, `ReadOnlyAccess` applies, and it includes some reads of stored data in services not listed below. AWS adds reads to it over time, and they reach the role without a stack update. Denies Better Stack adds to this template later reach a stack only when you update it; Better Stack also applies them from its own side on every session it starts. If you don't want this, deploy with `AllowConfigurationValues=false`.

S3 object names and sizes are readable in the default setting (`s3:ListBucket`); their contents are not, except objects whose key has an `AWSLogs/` path segment (`AWSLogs/…` or `<prefix>/AWSLogs/…`), which is where AWS services such as load balancers, VPC Flow Logs and CloudTrail deliver their logs. Any other object you store under such a path is readable too.

With a customer managed KMS key, the default setting can decrypt through CloudWatch Logs, Lambda, S3, X-Ray, RDS, Step Functions and Glue, never directly or through any other service. So Lambda environment variables under your own key are readable.

### With `AllowConfigurationValues=false`

The role has no `ReadOnlyAccess`. It reads exactly this list, minus the configuration-value reads denied below:

- CloudWatch alarms, metrics and log events, and Logs Insights queries
- EC2, Auto Scaling, ECS, EKS, Batch and Lambda descriptions
- RDS, DynamoDB and ElastiCache descriptions; S3 bucket names, locations and tags; EFS file systems
- Load balancers, API Gateway configuration and Route 53 zones
- SQS, SNS, Kinesis and Firehose metadata; Step Functions and EventBridge
- CloudTrail trails and event history (`LookupEvents`), AWS Health events, X-Ray traces
- CloudFormation stacks and their resources' status, not their `Metadata`, Application Auto Scaling, the account alias and enabled regions
- Its own role and policies, and the stack's two deny policies (`iam:GetRole` and the role policy reads on its own ARN, `iam:GetPolicy` and `iam:GetPolicyVersion` on the two policies' ARNs, nothing else), to tell which release it runs and what it allows
- `signin:CreateOAuth2Token` for AWS's MCP Server, which Better Stack calls with the role's session
- `kms:Decrypt` through CloudWatch Logs only, for log groups encrypted with your key

This role may need a stack update when AI SRE learns to use more services.

### Costs

Some reads cost money: Logs Insights and CloudTrail Lake queries are charged per GB scanned, `GetMetricData` per 1,000 metrics, and Cost Explorer (`ce:Get*`, default setting only) per request.

### What the role can't read

These reads are denied explicitly, in both settings, so that `ReadOnlyAccess` or a broader policy attached to the role later can't widen it:

- S3 objects, except under an `AWSLogs/` path segment, where AWS services deliver their logs; Secrets Manager secret values, SSM parameter values
- Lambda function code (`lambda:GetFunction`) and invocation
- DynamoDB items and streams, SQS messages, Kinesis records
- EC2 Windows passwords, site-to-site VPN connections (they carry the tunnels' pre-shared keys), unmasked CloudWatch Logs data
- API Gateway API keys, also through usage plans
- CloudWatch Omni's temporary credentials for a space (`cloudwatch:GetSpace*`: `GetSpaceCredentials`, `GetSpaceCredentialsForOrganization`, `GetSpaceDataAccess`)
- CloudWatch Omni query results (`cloudwatch:GetTelemetryQueryResults`), which can hold rows of a query someone else ran, even with `logs:Unmask`
- X-Ray sampling targets (`xray:GetSamplingTargets`), which report sampling statistics and change how X-Ray allocates your sampling quota
- Credentials and tokens other services hand out: ECR and CodeArtifact tokens, Cognito client secrets, tokens and identity credentials, API keys (AWS WAF, AppSync), Redshift, Lake Formation and S3 Access Grants credentials, Lightsail and GameLift access, IVS stream keys, Storage Gateway CHAP credentials
- More credentials and tokens: identity provider client secrets (Cognito, WorkSpaces Web), Amplify basic-auth credentials, MediaPackage ingest passwords, Chime and GameLift session tokens, push notification keys and device tokens (Pinpoint, SNS), CodePipeline job credentials, Snowball unlock codes and manifests, CloudHSM certificates, OpsWorks app keys, IoT Wireless device keys, IPAM verification tokens, Verified Access trust provider secrets, Managed Grafana workspaces, KMS key import parameters, Lightsail and RDS tenant database master user details, DMS endpoint passwords, the Directory Service RADIUS shared secret
- Query results and stored content: Athena results, OpenSearch documents, Keyspaces, DAX, QLDB, SimpleDB, Timestream, Redshift Data API results, Glacier, EBS snapshot blocks, HealthLake, Kinesis Video, IoT shadows and SiteWise values, SageMaker Feature Store records, Bedrock and Bedrock AgentCore memory and knowledge bases
- More stored content: Cloud Directory, CloudFront KeyValueStore, Data Exchange assets, DynamoDB vector search, Kendra, Personalize and Forecast queries, Fraud Detector events, Glue interactive session statements, IoT retained messages and topic rules, SES archived mail, Support case attachments, Transcribe jobs, Translate data, WorkDocs comments and versions, S3 on Outposts and MediaPackage objects, MediaLive input device thumbnails
- Payloads of Lambda durable executions
- End users of your product: Cognito user pools and sync records, Amazon Connect contact data and references, Lex sessions, Pinpoint endpoints, SES contact lists and suppressed addresses, opted-out phone numbers
- Code: Lambda layers, container images, CodeCommit files, diffs and comments, CodeArtifact packages, CloudFront functions, Greengrass component artifacts, Inspector code snippets
- Direct Connect virtual interfaces and router configurations (BGP keys), Interconnect connections and Client VPN configurations
- `kms:Decrypt` directly, or through any service other than CloudWatch Logs, Lambda, S3, X-Ray, RDS, Step Functions and Glue

With `AllowConfigurationValues=false`, nothing allows `kms:Decrypt` through any service but CloudWatch Logs, so resources under your own key stay unreadable there unless your key policy grants the role directly. Lambda decrypts a function's environment variables as the caller, so environment variables under the default `aws/lambda` key are readable in both settings.

The template's [CI](#template-contract) keeps [`read-only-access-review.tsv`](read-only-access-review.tsv), a reviewed verdict on every action `ReadOnlyAccess` and the inline policies grant, and fails when AWS adds one that hasn't been reviewed yet. `ReadOnlyAccess` is large, and the review can miss a read that returns secrets or stored data.

### Content like logs

With `AllowConfigurationValues=true`, the role can also read two kinds of content, which Better Stack treats like logs rather than configuration:

- Support cases (`support:DescribeCases`, `DescribeCommunication`, `DescribeCommunications`, `SearchForCases`). These return whatever you or your team pasted into a case.
- CodeBuild command executions (`codebuild:BatchGetCommandExecutions`, `ListCommandExecutionsForSandbox`). These return the commands' output.

With `AllowConfigurationValues=false`, the role can't read either.

### Configuration values

Read-only isn't secret-free. With `AllowConfigurationValues=true`, the default, configuration values are readable across AWS services. For example, the role can read Lambda, Lambda MicroVM, ECS and Batch environment variables (including ECS Express services, ECS daemons and Batch service job requests), EC2, Spot and Auto Scaling user data, CloudFormation parameters that aren't `NoEcho`, outputs, resources' `Metadata` such as `AWS::CloudFormation::Init` (which `NoEcho` doesn't mask, so a `NoEcho` value a template puts there is readable) and the resource properties in stack events, drift results, stack sets and Cloud Control resource listings, EventBridge target inputs, API Gateway stage variables, Firehose destination settings (for a Splunk destination that includes the HEC token, unless the stream reads it from Secrets Manager) EKS add-on configuration values, CodeBuild, App Runner, Amplify and Elastic Beanstalk environment settings, Systems Manager documents and AppConfig configurations. These are often where a misconfiguration shows. It can also read:

- Glue job definitions, including a repository access token when a job's source control uses a personal access token (`glue:GetJob`, `GetJobs`, `BatchGetJobs`)
- CodeBuild projects, including the secret token of a project's webhook (`codebuild:BatchGetProjects`)
- EMR clusters, including the Kerberos KDC admin, cross-realm trust and Active Directory join passwords of a cluster that uses Kerberos (`elasticmapreduce:DescribeCluster`)
- Security Hub findings, whose resource details copy configuration such as environment variables, pending database master passwords and OpenSearch master user passwords (`securityhub:GetFindings`)
- Step Functions and SWF execution input and output (`states:DescribeExecution`, `states:GetExecutionHistory`, `swf:GetWorkflowExecutionHistory`)
- IoT command payloads (`iot:GetCommand`)
- CloudWatch telemetry pipeline configurations (`observabilityadmin:GetTelemetryPipeline`)
- Cloud Control resource request status, which carries the resource's properties (`cloudformation:ListResourceRequests`, `GetResourceRequestStatus`)

With `AllowConfigurationValues=false`, the role has no `ReadOnlyAccess` at all, and each of these reads is either denied or not granted. The ones the role's fixed list would otherwise grant are denied explicitly:

`lambda:ListFunctions`, `lambda:ListVersionsByFunction`, `lambda:GetFunctionConfiguration`, `ecs:DescribeTaskDefinition`, `ecs:DescribeTasks`, `ecs:DescribeExpressGatewayService`, `ecs:DescribeDaemonTaskDefinition`, `batch:DescribeJobDefinitions`, `batch:DescribeJobs`, `batch:DescribeServiceJob`, `lambda:ListMicrovmImageVersions`, `ec2:DescribeInstanceAttribute`, `ec2:DescribeLaunchTemplateVersions`, `ec2:DescribeSpotFleetRequests`, `ec2:DescribeSpotInstanceRequests`, `autoscaling:DescribeLaunchConfigurations`, `cloudformation:DescribeStacks`, `cloudformation:DescribeChangeSet`, `cloudformation:DescribeStackResource`, `cloudformation:DescribeStackEvents`, `cloudformation:DescribeEvents`, `cloudformation:ListExports`, `cloudformation:DescribeStackResourceDrifts`, `cloudformation:ListStackInstanceResourceDrifts`, `cloudformation:DescribeStackSet`, `cloudformation:DescribeStackInstance`, `cloudformation:ListResources`, `cloudformation:ListResourceRequests`, `eks:DescribeAddon`, `events:ListTargetsByRule`, `firehose:DescribeDeliveryStream`, and API Gateway stages (`/restapis/*/stages*`, `/apis/*/stages*`).

The rest, such as Glue jobs, CodeBuild projects, EMR clusters, Security Hub findings, Step Functions and SWF executions, IoT commands and telemetry pipelines, aren't granted at all: they're outside the fixed list, so no deny is needed.

AI SRE then can't see configuration changes in those services, or a stack's deployment history: stack events carry each resource's properties. CloudTrail event history stays readable in both settings, and the request parameters AWS records there for some calls can include configuration values. A later release that adds a read to this list is a fix to the same rule.

## Upgrade

A stack's policy changes only when you update it. To move to the latest release, open the stack in the CloudFormation console, choose **Update stack**, **Replace existing template**, give the template URL `https://better-stack-cloudformation.s3.amazonaws.com/better-stack-ai-sre.yaml`, and keep the parameters. The role keeps its name and ARN. If an update fails, delete the stack and deploy it again from Better Stack: the stack, the role and the external ID come out the same.

## Cleanup

Delete the stack. That deletes the role, and Better Stack can no longer read anything in the account.

```bash
aws cloudformation delete-stack --stack-name betterstack-ai-sre-XXXXXXXX
```

## Template contract

Better Stack, setup links already sent, stacks updated in place and roles rebuilt in other tools depend on these, so no release changes them:

- Parameters are only ever added, always with a default. None is renamed or removed.
- The role name expression and the `ExternalId` pattern never change.
- The tag key `BetterStackAiSreTemplateVersion` never changes.
- The trust is two statements: `sts:AssumeRole` with the external ID and the callers' path conditions, and `sts:SetSourceIdentity` with the callers' path and a source identity starting `bs-`. No other `sts` action is ever added.
- Better Stack's role session names start with `BetterStackAiSre-`.
- Better Stack's source identity values start with `bs-`, and always will.
- The deny policies `better-stack-ai-sre-deny-data-<8 hex>` and `better-stack-ai-sre-deny-stored-data-<8 hex>` keep their names and stay attached to the role in both settings.

[`contract.json`](contract.json) records these fields. CI lints the template with cfn-lint, checks it against the contract (`test/check_contract.py`), checks the reviewed `ReadOnlyAccess` list (`test/check_read_only_access_review.py --static`), and runs the tests of those checks and of the policy simulator script:

```bash
cd cloudformation/ai-sre/test
pip install cfn-lint pyyaml
cfn-lint ../better-stack-ai-sre.yaml
python check_contract.py
python check_read_only_access_review.py --static
python -m unittest -v
```

The [ReadOnlyAccess drift workflow](../../.github/workflows/ai-sre-read-only-access-drift.yml) runs daily and on changes to this directory: it reads `ReadOnlyAccess`'s default version, expands it and the inline policies' wildcards against [AWS's service reference](https://servicereference.us-east-1.amazonaws.com/), and fails on any action the reviewed list has no line for.

`test/simulate_policy.py` asserts every allowed read and every explicit deny on a deployed role with IAM's policy simulator; the [E2E AI SRE workflow](../../.github/workflows/e2e-ai-sre.yml) deploys the stack, runs it with both settings of `AllowConfigurationValues`, and deletes the stack.

```bash
pip install boto3
python simulate_policy.py --role-arn arn:aws:iam::<account>:role/better-stack-ai-sre-role-<8 hex> --allow-configuration-values true
```
