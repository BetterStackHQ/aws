# Better Stack AI SRE

`better-stack-ai-sre.yaml` creates one read-only IAM role that Better Stack AI SRE assumes to investigate incidents in your AWS account. The stack has no other resources: no Lambda functions, no buckets, nothing that runs or stores data.

See the [main README](../../README.md) for the rest of this repository.

## Deploy

Better Stack gives you a link that opens the AWS console's quick-create page with this template and your parameters filled in. Review the stack there, acknowledge that it creates a named IAM role, and create it. Better Stack finds the role by itself; there is nothing to paste back.

The latest release is published at `https://better-stack-cloudformation.s3.amazonaws.com/better-stack-ai-sre.yaml`, and every release at `https://better-stack-cloudformation.s3.amazonaws.com/<version>/better-stack-ai-sre.yaml`, which is never overwritten. You can deploy either one yourself:

```bash
aws cloudformation deploy \
  --template-file better-stack-ai-sre.yaml \
  --stack-name betterstack-ai-sre-XXXXXXXX \
  --parameter-overrides ExternalId=bs-ai-sre-XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX \
  --capabilities CAPABILITY_NAMED_IAM
```

The stack can be deployed in any region; IAM roles are global.

## What it creates

One IAM role, `better-stack-ai-sre-role-<8 hex>`, where `<8 hex>` is the first eight hex digits after `bs-ai-sre-` in the external ID. It's tagged `Solution: BetterStack` and `BetterStackAiSreTemplateVersion: <release>`, the release of this template that made it. The stack output `IntegrationRoleArn` is its ARN.

Only Better Stack's AI SRE callers for the chosen environment can assume the role, and only with the external ID Better Stack generated for your integration. A second trust statement lets the same callers set a source identity and session tags; it grants no access by itself.

## Parameters

| Parameter | Default | Description |
|-----------|---------|-------------|
| `ExternalId` | (required) | Generated by Better Stack for your integration. Don't change it. |
| `BetterStackTeam` | `''` | The Better Stack team and organization that get access, shown in the role's description. Check it is yours. |
| `BetterStackEnvironment` | `production` | Which Better Stack environment may assume the role: `production`, `staging` or `development`. |
| `AllowConfigurationValues` | `true` | When `false`, denies every read Better Stack knows returns environment variables, user data or parameter values (see below). |
| `PermissionsBoundaryArn` | `''` | A permissions boundary your organization requires on new roles. Optional. |

## What the role can read

The role reads configuration and telemetry, never data or secrets:

- CloudWatch alarms, metrics and log events, and Logs Insights queries
- EC2, Auto Scaling, ECS, EKS, Batch and Lambda descriptions
- RDS, DynamoDB and ElastiCache descriptions; S3 bucket names, locations and tags; EFS file systems
- Load balancers, API Gateway configuration and Route 53 zones
- SQS, SNS, Kinesis and Firehose metadata; Step Functions and EventBridge
- CloudTrail trails and event history (`LookupEvents`), AWS Health events, X-Ray traces
- CloudFormation stacks and stack events, Application Auto Scaling, the account alias and enabled regions
- Its own role and policies (`iam:GetRole` and the policy reads on its own ARN only), to tell which release it runs
- `signin:CreateOAuth2Token` for AWS's MCP Server, which Better Stack calls with the role's session
- `kms:Decrypt` only through CloudWatch Logs, for log groups encrypted with your key

Two of these reads cost money: Logs Insights is charged per GB scanned and `GetMetricData` per 1,000 metrics.

### What the role can't read

An explicit deny, so that a broader policy attached to the role later can't widen it:

- S3 objects, Secrets Manager secret values, SSM parameter values
- Lambda function code (`lambda:GetFunction`) and invocation
- DynamoDB items, SQS messages, Kinesis records
- EC2 Windows passwords, site-to-site VPN connections (they carry the tunnels' pre-shared keys), unmasked CloudWatch Logs data
- API Gateway API keys, also through usage plans
- `kms:Decrypt` through any service other than CloudWatch Logs and Lambda

Lambda decrypts a function's environment variables as the caller, so Lambda is excepted from the `kms:Decrypt` deny: environment variables under the default `aws/lambda` key are readable. Under your own key they are not, since the role has no `kms:Decrypt` allow that reaches it (unless your key policy grants the role directly).

### Configuration values

Read-only isn't secret-free. With `AllowConfigurationValues=true`, the default, the role can read Lambda, ECS and Batch environment variables, EC2 and Auto Scaling user data, CloudFormation parameters that aren't `NoEcho`, outputs and the resource properties in stack events, EventBridge target inputs, API Gateway stage variables and Firehose destination settings. These are often where a misconfiguration shows.

With `AllowConfigurationValues=false`, the stack attaches a deny on every read Better Stack knows returns them:

`lambda:ListFunctions`, `lambda:ListVersionsByFunction`, `lambda:GetFunctionConfiguration`, `ecs:DescribeTaskDefinition`, `ecs:DescribeTasks`, `batch:DescribeJobDefinitions`, `batch:DescribeJobs`, `ec2:DescribeInstanceAttribute`, `ec2:DescribeLaunchTemplateVersions`, `ec2:DescribeSpotFleetRequests`, `autoscaling:DescribeLaunchConfigurations`, `cloudformation:DescribeStacks`, `cloudformation:DescribeChangeSet`, `cloudformation:DescribeStackEvents`, `cloudformation:ListExports`, `events:ListTargetsByRule`, `firehose:DescribeDeliveryStream`, and API Gateway stages (`/restapis/*/stages*`, `/apis/*/stages*`).

AI SRE then can't see configuration changes in those services, or a stack's deployment history: stack events carry each resource's properties. A later release that adds a read to this list is a fix to the same rule.

## Upgrade

A stack's policy changes only when you update it. To move to the latest release, open the stack in the CloudFormation console, choose **Update stack**, **Replace existing template**, give the template URL `https://better-stack-cloudformation.s3.amazonaws.com/better-stack-ai-sre.yaml`, and keep the parameters. The role keeps its name and ARN. If an update fails, delete the stack and deploy it again from Better Stack: the stack, the role and the external ID come out the same.

## Remove

Delete the stack. That deletes the role, and Better Stack can no longer read anything in the account.

```bash
aws cloudformation delete-stack --stack-name betterstack-ai-sre-XXXXXXXX
```

## Template contract

Better Stack, setup links already sent, stacks updated in place and roles rebuilt in other tools depend on these, so no release changes them:

- Parameters are only ever added, always with a default. None is renamed or removed.
- The role name expression and the `ExternalId` pattern never change.
- The tag key `BetterStackAiSreTemplateVersion` never changes.
- The trust keeps its two statements.
- Better Stack's role session names start with `BetterStackAiSre-`.

[`contract.json`](contract.json) records these fields. CI lints the template with cfn-lint, checks it against the contract (`test/check_contract.py`), and runs the tests of that check and of the policy simulator script:

```bash
cd cloudformation/ai-sre/test
pip install cfn-lint pyyaml
cfn-lint ../better-stack-ai-sre.yaml
python check_contract.py
python -m unittest -v
```

`test/simulate_policy.py` asserts every allowed read and every explicit deny on a deployed role with IAM's policy simulator; the [E2E AI SRE workflow](../../.github/workflows/e2e-ai-sre.yml) deploys the stack, runs it with both settings of `AllowConfigurationValues`, and deletes the stack.

```bash
pip install boto3
python simulate_policy.py --role-arn arn:aws:iam::<account>:role/better-stack-ai-sre-role-<8 hex> --allow-configuration-values true
```
