# Better Stack AI SRE

`better-stack-ai-sre.yaml` creates one read-only IAM role that Better Stack AI SRE assumes to investigate incidents in your AWS account, and two IAM policies that hold the role's denies. The stack has no other resources: no Lambda functions, no buckets, nothing that runs or stores data.

See the [main README](../../README.md) for the rest of this repository.

## Quick Start

Better Stack gives you a link that opens the AWS console's quick-create page with this template and your parameters filled in. Review the stack there, acknowledge that it creates a named IAM role, and create it. Better Stack finds the role by itself; there is nothing to paste back.

The latest release is published at `https://better-stack-cloudformation.s3.amazonaws.com/better-stack-ai-sre.yaml`, and every release at `https://better-stack-cloudformation.s3.amazonaws.com/<version>/better-stack-ai-sre.yaml`, which is never overwritten. You can download either one and deploy it yourself:

```bash
curl -fsSLO https://better-stack-cloudformation.s3.amazonaws.com/better-stack-ai-sre.yaml

aws cloudformation deploy \
  --template-file better-stack-ai-sre.yaml \
  --stack-name betterstack-ai-sre-XXXXXXXX \
  --parameter-overrides ExternalId=bs-ai-sre-XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX \
  --capabilities CAPABILITY_NAMED_IAM
```

The stack can be deployed in any region; IAM roles are global.

## What it creates

One IAM role, `better-stack-ai-sre-role-<8 hex>`, where `<8 hex>` is the first eight hex digits after `bs-ai-sre-` in the external ID. It's tagged `Solution: BetterStack` and `BetterStackAiSreTemplateVersion: <release>`, the release of this template that made it.

Only Better Stack's AI SRE callers for the chosen environment can assume the role, and only with the external ID Better Stack generated for your integration. A second trust statement lets the same callers set a source identity that starts with `bs-`, so that your CloudTrail can attribute AI SRE's calls; it grants no access by itself.

The stack also creates two customer managed policies, `better-stack-ai-sre-deny-data-<8 hex>` and `better-stack-ai-sre-deny-stored-data-<8 hex>`, attached to the role in both scopes. They hold the denies listed in [What the role can't read](#what-the-role-cant-read), which don't fit in the role's own inline policies. With `ReadScope=broad`, the role also has AWS's managed [`ReadOnlyAccess`](https://docs.aws.amazon.com/aws-managed-policy/latest/reference/ReadOnlyAccess.html) policy attached. The stack creates nothing else.

| Output | Description |

## Parameters

| Parameter | Default | Description |
|-----------|---------|-------------|
| `ExternalId` | (required) | Generated by Better Stack for your integration. Don't change it. |
| `BetterStackTeam` | `''` | The Better Stack team and organization that get access, shown in the role's description. Check it is yours. |
| `BetterStackEnvironment` | `production` | Which Better Stack environment may assume the role: `production`, `staging` or `development`. |
| `ReadScope` | `curated` | `curated`: a fixed list of reads Better Stack maintains. `broad`: AWS's `ReadOnlyAccess` as well. Both deny the reads [listed below](#what-the-role-cant-read) as known to return secrets, credentials, stored data, environment variables, user data, job definitions or stack parameters. With `broad`, `ReadOnlyAccess` can still expose such values through other services (see [Configuration values](#configuration-values)). |
| `PermissionsBoundaryArn` | `''` | A permissions boundary your organization requires on new roles. Optional. |

## What the role can read

`ReadScope` chooses between two roles. Both deny the same reads (see [What the role can't read](#what-the-role-cant-read)).

### With `ReadScope=curated`, the default

The role reads exactly this list:

- CloudWatch alarms, metrics and log events, and Logs Insights queries
- EC2 instances, volumes and networking, Auto Scaling groups, ECS clusters and services, EKS clusters, Batch job queues and job lists, and Lambda event source mappings and aliases, but not Lambda function configuration (see below)
- RDS, DynamoDB and ElastiCache descriptions; S3 bucket names, locations and tags; EFS file systems
- Load balancers, API Gateway configuration and Route 53 zones
- SQS, SNS, Kinesis and Firehose metadata; Step Functions and EventBridge
- CloudTrail trails and event history (`LookupEvents`), AWS Health events, X-Ray traces
- CloudFormation: the list of stacks with their status (`ListStacks`) and their resources' status (`DescribeStackResources`), but not stack parameters, outputs, templates or events; Application Auto Scaling, the account alias and enabled regions
- Its own role and policies, and the stack's two deny policies (`iam:GetRole` and the role policy reads on its own ARN, `iam:GetPolicy` and `iam:GetPolicyVersion` on the two policies' ARNs, nothing else), to tell which release it runs and what it allows
- `signin:CreateOAuth2Token` for AWS's MCP Server, which Better Stack calls with the role's session
- `kms:Decrypt` through CloudWatch Logs only, for log groups encrypted with your key

This role may need a stack update when AI SRE learns to use more services.

### With `ReadScope=broad`

The role also has AWS's [`ReadOnlyAccess`](https://docs.aws.amazon.com/aws-managed-policy/latest/reference/ReadOnlyAccess.html), which AWS extends as it adds services, plus the reads in the inline policy `BetterStackAiSreBroadAccess` that `ReadOnlyAccess` lacks: CloudTrail Lake queries, Performance Insights analysis reports, and the read-only tools of AWS's hosted EKS, ECS and Application Signals MCP servers. The reads in [What the role can't read](#what-the-role-cant-read) are denied on top. Some configuration values are readable, including other services' environment settings (see [Configuration values](#configuration-values)).

Outside the denied list, `ReadOnlyAccess` applies, and it includes some reads of stored data in services not listed below. AWS adds reads to it over time, and they reach the role without a stack update. Denies Better Stack adds to this template later reach a stack only when you update it; Better Stack also applies them from its own side on every session it starts.

S3 object names and sizes are readable (`s3:ListBucket`); their contents are not, except objects whose key has an `AWSLogs/` path segment (`AWSLogs/…` or `<prefix>/AWSLogs/…`), which is where AWS services such as load balancers, VPC Flow Logs and CloudTrail deliver their logs. Any other object you store under such a path is readable too. AWS Config's configuration history and snapshot files (`<prefix>/AWSLogs/<account>/Config/…`) are the exception: they copy the configuration values denied below, so they stay unreadable.

With a customer managed KMS key, the role can decrypt through CloudWatch Logs, S3, X-Ray, RDS, Step Functions and Glue, never directly or through any other service.

### Costs

Some reads cost money: Logs Insights and CloudTrail Lake queries are charged per GB scanned, `GetMetricData` per 1,000 metrics, and Cost Explorer (`ce:Get*`, `ReadScope=broad` only) per request.

### What the role can't read

Each read below is known to return secrets, credentials, stored data or configuration values that teams keep secrets in. They're denied explicitly, in both scopes, so that `ReadOnlyAccess` or a broader policy attached to the role later can't widen it:

- Where teams keep secrets in configuration: Lambda environment variables (`lambda:GetFunctionConfiguration`, `ListFunctions`, `ListVersionsByFunction`, `ListMicrovmImageVersions`), ECS task definitions and task overrides (`ecs:DescribeTaskDefinition`, `DescribeTasks`, `DescribeExpressGatewayService`, `DescribeDaemonTaskDefinition`), EC2 and Auto Scaling user data (`ec2:DescribeInstanceAttribute`, `DescribeLaunchTemplateVersions`, `DescribeSpotFleetRequests`, `autoscaling:DescribeLaunchConfigurations`), Batch job definitions and jobs (`batch:DescribeJobDefinitions`, `DescribeJobs`, `DescribeServiceJob`), and CloudFormation stack, change set and stack set parameters and resource `Metadata` (`cloudformation:DescribeStacks`, `DescribeChangeSet`, `DescribeStackSet`, `DescribeStackInstance`, `DescribeStackResource`)
- The reads that copy those values: Lambda MicroVM image versions and web function revisions (`lambda:GetMicrovmImageVersion`, `GetWebFunctionRevision`), launch template data and Spot requests (`ec2:GetLaunchTemplateData`, `DescribeSpotInstanceRequests`), stack templates and extension configurations (`cloudformation:GetTemplate`, `BatchDescribeTypeConfigurations`), stack events and drift results (`cloudformation:DescribeStackEvents`, `DescribeEvents`, `DescribeStackResourceDrifts`, `DetectStackResourceDrift`, `ListStackInstanceResourceDrifts`), Cloud Control resources and resource requests (`cloudformation:GetResource`, `ListResources`, `GetGeneratedTemplate`, `ListResourceRequests`, `GetResourceRequestStatus`), and AWS Config's recorded configuration items (`config:BatchGetResourceConfig`, `BatchGetAggregateResourceConfig`, `GetResourceConfigHistory`, `GetAggregateResourceConfig`, `SelectResourceConfig`, `SelectAggregateResourceConfig`, `GetResourceEvaluationSummary`)
- S3 objects, except under an `AWSLogs/` path segment, where AWS services deliver their logs, and even there AWS Config's configuration history and snapshots (`*/AWSLogs/*/Config/*`); Secrets Manager secret values, SSM parameter values
- Lambda function code (`lambda:GetFunction`) and invocation
- DynamoDB items and streams, SQS messages, Kinesis records
- EC2 Windows passwords, site-to-site VPN connections (they carry the tunnels' pre-shared keys), unmasked CloudWatch Logs data
- API Gateway API keys, also through usage plans
- CloudWatch Omni's temporary credentials for a space (`cloudwatch:GetSpace*`: `GetSpaceCredentials`, `GetSpaceCredentialsForOrganization`, `GetSpaceDataAccess`)
- CloudWatch Omni query results (`cloudwatch:GetTelemetryQueryResults`), which can hold rows of a query someone else ran, even with `logs:Unmask`
- X-Ray sampling targets (`xray:GetSamplingTargets`), which report sampling statistics and change how X-Ray allocates your sampling quota
- Security Hub CSPM's organizations import status (`securityhub:GetCSPMOrganizationsImportStatus`), until AWS documents what it returns
- Credentials and tokens other services hand out: ECR and CodeArtifact tokens, Cognito client secrets, tokens and identity credentials, API keys (AWS WAF, AppSync), Redshift, Lake Formation and S3 Access Grants credentials, Lightsail and GameLift access, IVS stream keys, Storage Gateway CHAP credentials
- Pre-signed upload URLs of pending import jobs (Cognito user imports, SES Mail Manager address lists) and the SSM Agent's Run Command channel (`ec2messages:GetMessages`)
- More credentials and tokens: identity provider client secrets (Cognito, WorkSpaces Web), Amplify basic-auth credentials, MediaPackage ingest passwords, Chime and GameLift session tokens, push notification keys and device tokens (Pinpoint, SNS), CodePipeline job credentials, Snowball unlock codes and manifests, CloudHSM certificates, OpsWorks app keys, IoT Wireless device keys, IPAM verification tokens, Verified Access trust provider secrets, Managed Grafana workspaces, KMS key import parameters, Lightsail and RDS tenant database master user details, DMS endpoint passwords, the Directory Service RADIUS shared secret
- Query results and stored content: Athena results, OpenSearch documents, Keyspaces, DAX, QLDB, SimpleDB, Timestream, Redshift Data API results, Glacier, EBS snapshot blocks, HealthLake, Kinesis Video, IoT shadows and SiteWise values, SageMaker Feature Store records, Bedrock and Bedrock AgentCore memory and knowledge bases, stored Bedrock inference requests (`bedrock-mantle:GetInference`)
- More stored content: Cloud Directory, CloudFront KeyValueStore, Data Exchange assets, DynamoDB vector search, Kendra, Personalize and Forecast queries, Fraud Detector events, Glue interactive session statements, IoT retained messages and topic rules, SES archived mail, Support case attachments, Transcribe jobs, Translate data, WorkDocs comments and versions, S3 on Outposts and MediaPackage objects, MediaLive input device thumbnails
- Payloads of Lambda durable executions
- End users of your product: Cognito user pools and sync records, Amazon Connect contact data and references, Lex sessions, Pinpoint endpoints, SES contact lists, suppressed addresses and message exports, opted-out phone numbers
- Code: Lambda layers, container images, CodeCommit files, diffs and comments, CodeArtifact packages, CloudFront functions, Greengrass component artifacts, Inspector code snippets
- Direct Connect virtual interfaces and router configurations (BGP keys), Interconnect connections and Client VPN configurations
- `kms:Decrypt` directly, or through any service other than CloudWatch Logs, S3, X-Ray, RDS, Step Functions and Glue

These denies also hide the other fields the same calls return: a Lambda function's runtime, timeout, memory and state; an ECS task definition's image, CPU and memory, and a task's stopped reason and exit codes; a Batch job definition and a job's container details; a launch template's contents; a stack's outputs, its template and its deployment history (stack events); drift results; and AWS Config's configuration history. AWS has no narrower call for most of these. AI SRE uses what it can instead: stack and resource status and reasons (`cloudformation:ListStacks`, `DescribeStackResources`), task and job lists (`ecs:ListTasks`, `ecs:DescribeServices` events, `batch:ListJobs`, which includes each job's status, reason and exit code), CloudWatch metrics, and CloudTrail event history (`LookupEvents`), which shows what changed and who changed it.

With `ReadScope=curated`, nothing allows `kms:Decrypt` through any service but CloudWatch Logs, so resources under your own key stay unreadable there unless your key policy grants the role directly.

The template's [CI](#template-contract) keeps [`read-only-access-review.tsv`](read-only-access-review.tsv), a reviewed verdict on every action `ReadOnlyAccess` and the inline policies grant, and fails when AWS adds one that hasn't been reviewed yet. `ReadOnlyAccess` is large, and the review can miss a read that returns secrets or stored data. With `ReadScope=broad`, `ReadOnlyAccess` can still expose such values through other services: [Configuration values](#configuration-values) lists those found so far.

### Content like logs

With `ReadScope=broad`, the role can also read two kinds of content, which Better Stack treats like logs rather than configuration:

- Support cases (`support:DescribeCases`, `DescribeCommunication`, `DescribeCommunications`, `SearchForCases`). These return whatever you or your team pasted into a case.
- CodeBuild command executions (`codebuild:BatchGetCommandExecutions`, `ListCommandExecutionsForSandbox`). These return the commands' output.

With `ReadScope=curated`, the role can't read either.

### Configuration values

Read-only isn't secret-free. With `ReadScope=broad`, these configuration values are readable, because they're often where a misconfiguration shows: stack exports, EventBridge target and subscriber inputs, API Gateway stage variables, Firehose destination settings (for a Splunk destination that includes the HEC token, unless the stream reads it from Secrets Manager), EKS add-on configuration values, and, through `ReadOnlyAccess`, other services' environment settings and configuration: CodeBuild, App Runner, Amplify and Elastic Beanstalk environment settings, Systems Manager documents and AppConfig configurations. A team can keep a secret in any of these. `ReadOnlyAccess` can still expose such values through other services as well. Those found so far include:

- Stack parameters that other services pass to CloudFormation: CodePipeline's CloudFormation deploy actions (`codepipeline:GetPipeline`, `ParameterOverrides`), Service Catalog provisioned product plans (`servicecatalog:DescribeProvisionedProductPlan`) and SageMaker projects (`sagemaker:DescribeProject`)
- EC2 user data in Image Builder image recipes (`imagebuilder:GetImageRecipe`, `userDataOverride`)
- AWS Config configuration items in a CloudTrail Lake event data store, where a team has one (`cloudtrail:StartQuery`, `GetQueryResults`). These aren't denied: IAM scopes CloudTrail Lake queries to an event data store's ARN, with no condition on what the store holds, so a deny would block every CloudTrail Lake query, not only these
- Glue job definitions, including a repository access token when a job's source control uses a personal access token (`glue:GetJob`, `GetJobs`, `BatchGetJobs`)
- CodeBuild projects, including the secret token of a project's webhook (`codebuild:BatchGetProjects`)
- EMR clusters, including the Kerberos KDC admin, cross-realm trust and Active Directory join passwords of a cluster that uses Kerberos (`elasticmapreduce:DescribeCluster`)
- Security Hub findings, whose resource details copy configuration such as environment variables, pending database master passwords and OpenSearch master user passwords (`securityhub:GetFindings`)
- Step Functions and SWF execution input and output (`states:DescribeExecution`, `states:GetExecutionHistory`, `swf:GetWorkflowExecutionHistory`)
- IoT command payloads (`iot:GetCommand`)
- CloudWatch telemetry pipeline configurations (`observabilityadmin:GetTelemetryPipeline`)
- Lightsail container services' environment variables (`lightsail:GetContainerServices`, `GetContainerServiceDeployments`)
- CodeBuild builds' environment variables (`codebuild:BatchGetBuilds`)
- SageMaker training jobs', models' and processing jobs' environment variables (`sagemaker:DescribeTrainingJob`, `DescribeModel`, `DescribeProcessingJob`)
- EMR Serverless job runs' arguments and configuration (`emr-serverless:GetJobRun`)

With `ReadScope=curated`, the role has no `ReadOnlyAccess` at all, and each of these reads is either denied or not granted. The ones the role's fixed list would otherwise grant are denied explicitly:

`cloudformation:ListExports`, `eks:DescribeAddon`, `events:ListTargetsByRule`, `events:DescribeSubscriber`, `firehose:DescribeDeliveryStream`, and API Gateway stages (`/restapis/*/stages*`, `/apis/*/stages*`).

The rest, such as CodeBuild projects, Glue jobs, EMR clusters, Security Hub findings, Step Functions and SWF executions, IoT commands and telemetry pipelines, aren't granted at all: they're outside the fixed list, so no deny is needed.

Unlike the reads above, CloudTrail event history (`LookupEvents`) stays readable in both scopes, `curated` included, and the request parameters AWS records there can include configuration values: the parameter values of `CreateStack` and `UpdateStack` calls, except `NoEcho` ones, and the container definitions of `RegisterTaskDefinition` calls. A later release that adds a read to this list is a fix to the same rule.

## Upgrade

A stack's policy changes only when you update it. To move to the latest release, open the stack in the CloudFormation console, choose **Update stack**, **Replace existing template**, give the template URL `https://better-stack-cloudformation.s3.amazonaws.com/better-stack-ai-sre.yaml`, and keep the parameters. The role keeps its name and ARN. If an update fails, delete the stack and deploy it again from Better Stack: the stack, the role and the external ID come out the same.

From v1.2.0, `ReadScope` replaces `AllowConfigurationValues`. CloudFormation drops the value of a parameter the new template doesn't have, and gives a new parameter its default, so a v1.2.0 stack becomes `ReadScope=curated` unless you set `broad`:

- A stack deployed with `AllowConfigurationValues=false` keeps the same curated role, with the new denies.
- A stack deployed with `AllowConfigurationValues=true` (v1.2.0's default) loses `ReadOnlyAccess`. To keep it, set `ReadScope` to `broad` on the **Specify stack details** page of the update.

With the AWS CLI, pass `UsePreviousValue=true` for the other parameters only: naming `AllowConfigurationValues` fails the update, because the new template doesn't declare it.

## Cleanup

Delete the stack. That deletes the role, and Better Stack can no longer read anything in the account.

```bash
aws cloudformation delete-stack --stack-name betterstack-ai-sre-XXXXXXXX
```

## Template contract

Better Stack, setup links already sent, stacks updated in place and roles rebuilt in other tools depend on these, so no release changes them:

- Parameters are only ever added, always with a default. None is renamed or removed.
- The role name expression and the `ExternalId` pattern never change.
- The tag key `BetterStackAiSreTemplateVersion` never changes.
- The trust is two statements: `sts:AssumeRole` with the external ID and the callers' path conditions, and `sts:SetSourceIdentity` with the callers' path and a source identity starting `bs-`. No other `sts` action is ever added.
- Better Stack's role session names start with `BetterStackAiSre-`.
- Better Stack's source identity values start with `bs-`, and always will.
- The deny policies `better-stack-ai-sre-deny-data-<8 hex>` and `better-stack-ai-sre-deny-stored-data-<8 hex>` keep their names and stay attached to the role in both scopes.

[`contract.json`](contract.json) records these fields. CI lints the template with cfn-lint, checks it against the contract (`test/check_contract.py`), checks the reviewed `ReadOnlyAccess` list (`test/check_read_only_access_review.py --static`), and runs the tests of those checks and of the policy simulator script:

```bash
cd cloudformation/ai-sre/test
pip install cfn-lint pyyaml
cfn-lint ../better-stack-ai-sre.yaml
python check_contract.py
python check_read_only_access_review.py --static
python -m unittest -v
```

The [ReadOnlyAccess drift workflow](../../.github/workflows/ai-sre-read-only-access-drift.yml) runs daily and on changes to this directory: it reads `ReadOnlyAccess`'s default version, expands it and the inline policies' wildcards against [AWS's service reference](https://servicereference.us-east-1.amazonaws.com/), and fails on any action the reviewed list has no line for.

`test/simulate_policy.py` asserts every allowed read and every explicit deny on a deployed role with IAM's policy simulator; the [E2E AI SRE workflow](../../.github/workflows/e2e-ai-sre.yml) deploys the stack, runs it with both values of `ReadScope`, and deletes the stack.

```bash
pip install boto3
python simulate_policy.py --role-arn arn:aws:iam::<account>:role/better-stack-ai-sre-role-<8 hex> --read-scope curated
```
